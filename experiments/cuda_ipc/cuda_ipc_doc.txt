Passing CUDA IPC meta to python
<Bobby Wang bobwang@nvidia.com> 2022/07/01


Goal
The underlying mapInPandas needs to serialize the whole CUDF table into the buffer with Apache Arrow IPC Stream format and pass it to the python process, which is quite an expensive overhead.


It’s inevitable to communicate between the java process and the python process, so if we just pass some meta-information instead of the real data, it should help the performance[a].


Design
The below picture is demonstrating the original communication between the java and the python process.




  



The GpuMapInPandasExec serializes the whole ColumnarBatch (cudf table) into the ArrowRecordBatch, basically, it first copies the data into the Host Memory from GPU memory and then copies the Host Memory into the ArrowRecordBatch, finally passes all the data into python process. After deserializing the data, the pandas_udf is called to handle the pandas DataFrame.


While the below picture shows how to just pass the CUDA IPC information instead of the real data
  



* Java Process
1. Iterate all the ColumnarBatches
2. Get the CUDA IPC information from each ColumnarBatch (we can add a configuration to control if doing this way)
3. Write the IPC information as rows of data in Apache Arrow


* Python Process
1. Deserialize the Arrow data and convert it to pandas dataframe.
2. Get the CUDA IPC information from the first row of the pandas dataframe.
3. Re-construct cudf table according to the cuda IPC information.


So, with this, the java process just passes the meta info which is supposed to be pretty small, and the performance should be improved.


The CUDA IPC meta information is a JSON format, which includes all the information about the serialized columns and the whole contiguous buffer’s CUDA IPC handle. When decoding, we first need to get the whole gpu buffer data address by opening the IPC handle specified by “gpuDataPtr”, and then we can get column data pointer by adding the “dataOffset” on the whole gpu buffer and so on.


For this solution, we pass the encoded CUDA IPC handle string by base64 to the python process from the JVM process. Take two int ColumnVector without nulls as an example, the CUDA IPC meta information is like,

The getCudaIpcMemHandle java API is https://github.com/wbo4958/spark-rapids-jni/blob/cuda-ipc/src/main/java/com/nvidia/spark/rapids/jni/CudaIPC.java#L35 and the native implementation is https://github.com/wbo4958/spark-rapids-jni/blob/cuda-ipc/src/main/cpp/src/CudaIPCJni.cpp#L28 
Pros and cons
Pros:
The solution is based on the existing mechanism of pandas_udf, and we serialize the meta info into the Arrow data, so we don’t need to change the protocol itself, and what’s more, It requires less code changing.
Cons:
1. Users can’t manipulate the pandas dataframe which contains the IPC information instead of the real data. So we may provide the function in RAPIDS Accelerator to convert the IPC information to cudf to pandas dataframe.
2. In the java process, we may need to iterate all the ColumnarBatches and get the corresponding IPC information, which means we can’t release it immediately after getting the IPC info for one ColumnarBatch. Finally, it may blow up the GPU memory rapidly.

def ctypes2cupy(cptr, length, dtype):
   """Convert a ctypes pointer array to a cupy array."""
   # pylint: disable=import-error
   import cupy
   from cupy.cuda.memory import MemoryPointer
   from cupy.cuda.memory import UnownedMemory

   CUPY_TO_CTYPES_MAPPING = {
       cupy.float64: ctypes.c_double,
       cupy.float32: ctypes.c_float,
       cupy.uint32: ctypes.c_uint,
       cupy.int32: ctypes.c_int,
   }
   if dtype not in CUPY_TO_CTYPES_MAPPING:
       raise RuntimeError(f"Supported types: {CUPY_TO_CTYPES_MAPPING.keys()}")
   addr = cptr  # ctypes.cast(cptr, ctypes.c_void_p).value
   # pylint: disable=c-extension-no-member,no-member
   device = cupy.cuda.runtime.pointerGetAttributes(addr).device
   # The owner field is just used to keep the memory alive with ref count.  As
   # unowned's life time is scoped within this function we don't need that.
   unownd = UnownedMemory(
       addr, length * ctypes.sizeof(CUPY_TO_CTYPES_MAPPING[dtype]), owner=None
   )
   memptr = MemoryPointer(unownd, 0)
   # pylint: disable=unexpected-keyword-arg
   mem = cupy.ndarray((length,), dtype=dtype, memptr=memptr)
   assert mem.device.id == device
   arr = cupy.array(mem, copy=True)
   return arr


def mapInPandas_SQL_MAP_PANDAS_ITER_UDF(spark):
   spark.conf.set("spark.rapids.sql.python.arrow.zerocopy.enabled", "true")
   spark.conf.set("spark.rapids.sql.python.arrow.zerocopy.rebatching.enabled", "true")

   def print_data(meta):
       import json
       import base64
       import cupy
       json_str = json.loads(meta)
       ipc_handle_str = json_str['gpuDataPtr']
       ipc_handle_bytes = base64.b64decode(ipc_handle_str)
       d_ptr = cupy.cuda.runtime.ipcOpenMemHandle(ipc_handle_bytes)
       print(f"Pandas Dataframe row is: {json_str}")
       for column in json_str["serializedColumns"]:
           data_offset = column["dataOffset"]
           row_count = column['size']
           array = ctypes2cupy(d_ptr + data_offset, row_count, np.int32)
           print(f"Gpu Data is: {array}")

Question


According to the cuda interprocess communication doc, the IPC handle should be the same for any pointer address in the allocated memory, which I have verified. 


Eg, if the allocated GPU memory is [ptr, ptr + 1024], then the IPC handle is the same for cudaIpcGetMemHandle(ptr) or cudaIpcGetMemHandle(ptr + 4).


The API cv.getDeviceBufferFor(BufferType.DATA).getAddress() will get the data address from column_view in native.


T const* head() const noexcept
{
 return static_cast<T const*>(_data);
}


T const* data() const noexcept
{
return head<T>() + _offset;
}
	

The column_view has a constructor like the below code shown,
column_view(data_type type,
          size_type size,
          void const* data,
          bitmask_type const* null_mask            = nullptr,
          size_type null_count                     = UNKNOWN_NULL_COUNT,
          size_type offset                         = 0,
          std::vector<column_view> const& children = {});
	

which accepts the data address and the offset. So here is the question, is it possible that the data address is already calculated with offset from the beginning? Eg, The allocated GPU memory is [ptr, ptr + 1024], while the data address in the column_view is ptr + 4, the offset in column_view is 0. In this case, seems we can’t get the real beginning address ptr, then the IPC handle will be broken.


Discussion
The RebatchingRoundOffIterator may call Table.contiguousSplit() in some cases which results in all the columns will be packed into a single allocated GPU buffer with the serialized column meta info including the data offset, validity offset, null count, data type, and so on. So that explains why I got the same CUDA IPC handle for different columns.


The new way is to pass the serialized column meta information and the CUDA IPC handle for the single GPU buffer to another process, in which we can decode the gpu address of the single column by adding the data offset on the whole gpu buffer.
